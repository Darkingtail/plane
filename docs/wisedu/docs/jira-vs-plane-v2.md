### 1.3 GitLab 自动化工作流

在研发自动化的核心链条上，Plane 采用全新的架构设计，对原有的自动化体系进行了降维重构。

| 能力                     | 盗版 Jira + jirascripts | Plane + gitlab-bridge | 差距             |
| ------------------------ | ----------------------- | --------------------- | ---------------- |
| 状态变更触发分支操作     | ✅                      | ✅                    | 无               |
| 分支自动创建             | ✅                      | ✅                    | 无               |
| 联调合并（feature→dev）  | ✅                      | ✅                    | 无               |
| 提测合并（feature→test） | ✅                      | ✅                    | 无               |
| 封版/发版流程            | ✅                      | ✅                    | 无               |
| API 稳定性               | ⚠️ 黑盒，随时失效       | ✅ 开放 REST API      | **Plane 更好**   |
| Webhook 认证             | 账号密码明文            | Token 认证            | **Plane 更安全** |

**架构对比优势：**
原有的 `jirascripts` 是由于 Jira API 黑盒和扩展困难，被迫建立的“重型系统”（包含独立的前端页面、后端逻辑和数据库），维护成本极高且容易产生状态不同步。
新的 `gitlab-bridge` 则是一个**轻量级的无状态微服务**。它充分利用了 Plane 原生完善的 Webhook 机制与开放的 REST API 接口，只做“粘合剂”的转发与轻量编排，无需自身存储中间状态。这不仅消除了原系统的历史技术债，更保障了研发工作流的高内聚和低耦合。

### 1.5 AI 原生开发工作流（Plane 独有优势）

盗版 Jira 在此维度没有任何可比性，这是 Plane 对未来研发范式的根本性领先。

Plane 原生支持 MCP 协议（`plane-mcp-server`，55+ 工具），AI 编码工具可直接读写任务数据，这使得**全链路 AI 开发工作流**成为可能：

```
需求录入 → 需求分析 → 需求实现 → 需求验证 → 需求测试
  AI 生成      AI 拆解     AI 编码     AI 回写      AI 验收
```

| 阶段     | 传统方式            | Plane + AI                            |
| -------- | ------------------- | ------------------------------------- |
| 需求录入 | 人工填写 Issue      | AI 对话式录入，自动结构化为 Issue     |
| 需求分析 | 人工拆分子任务      | AI 读取 Issue，自动拆解 Sub Work Item |
| 需求实现 | 开发者手动编码      | AI 领取任务、编码、提交 MR，全程自动  |
| 需求验证 | 人工 Code Review    | AI 回写 Issue 状态、评论实现摘要      |
| 需求测试 | 人工测试 + 回填结果 | AI 生成测试用例，执行后自动更新 Issue |

**为什么必须是 Plane**：盗版 Jira 的 API 黑盒、无 MCP 支持，使得任何 AI 工具都无法稳定接入。Plane 的开放 API + 官方 MCP Server 是这条路线的必要基础设施。

## 二、Plane 架构优势与团队掌控力论证

除了功能层面的对比，我们需要从底层架构和工程设计的角度，论证“为什么选择对 Plane 进行二次开发（Plane Forge）是一条可持续、高投产比的技术路线”。

### 2.1 现代化的技术栈底座

与 Jira 沉重且封闭的 Java 遗留架构不同，Plane 采用的是当前最为主流、高效的现代化技术栈，具有极强的生命力：

- **前端工程化（React + MobX + Turbo）**：采用 Turbo Monorepo 组织结构，前端基于 React Router 7（原 Remix）+ Vite，使用 MobX 进行轻量化状态管理，Tailwind CSS 负责原子化样式。相比传统 React+Redux，这套组合开发效率更高、组件复用率极大（如 `@plane/ui` 独立包），大幅降低了我们修改 UI 或注入新页面的成本。
- **后端强基建（Django + DRF）**：后端采用成熟的 Python Django 框架及 Django REST Framework。Django 提供了开箱即用的 ORM、强大的 Admin 自动管理后台以及严格的安全验证机制。
- **基础设施标准（PostgreSQL + Redis + Minio）**：使用 PostgreSQL 作为主关系型数据库，Redis 处理缓存及 Celery 异步任务，Minio 作为对象存储。这套基建不仅性能上限高，而且完全适配私有化部署和微服务扩展。

### 2.2 极致的二开友好度（Plane Forge 的可行性）

我们在对 Plane 源码进行深度调研后，确认了其高度可维护的工程布局：

1.  **架构解耦清晰**：其 Monorepo 的包管理模式（`apps` 与 `packages` 分离），使得我们在 `apps/web` 注入自定义页面（如 GitLab 配置页），或在 `apps/api` 扩展后端逻辑时，不会破坏其核心渲染包或 UI 组件库。
2.  **纯净的 REST 开放体系**：所有前端操作均依赖标准且全量暴露的 API 接口，这使得第三方微服务（如我们的 `gitlab-bridge`）能够极其自然地作为外部客户端接入。
3.  **自主升级可控**：项目结构规整，跟进上游（Upstream）的安全补丁和新特性合并时，我们的定制化代码产生严重冲突的概率被控制在最低限度。

## 三、Plane 的不足与应对

诚实列出 Plane CE 当前的不足及我们的应对策略：

| 不足               | 严重程度 | 应对方案                               |
| ------------------ | -------- | -------------------------------------- |
| 自定义字段 CE 没有 | 🟡 中    | 源码二开实现                           |
| Epic 不是原生概念  | 🟢 低    | Module 平替，团队偶尔用，可接受        |
| 迁移学习曲线       | 🟢 低    | UI 现代直观，培训成本低                |
| 历史数据迁移       | 🟢 低    | 历史 Jira 数据归档，新项目直接用 Plane |

> **说明**：经实测与调研，网络上流传的“Plane CE 版存在 12 人用户数量上限”**系错误信息**。开源 CE 版本并未对此进行任何限制，无需进行源码破解即可满足任意规模团队的使用。

## 四、替代必要性论证

### 4.1 继续用盗版 Jira 的代价

**合规风险（最高优先级，无法通过技术手段消除）**

使用盗版软件违反《计算机软件保护条例》。随着公司业务发展、对外商业合作增多，尽职调查中发现盗版使用将直接影响融资、合作和上市进程。这是一颗定时炸弹，且风险随公司规模增长线性放大。

**技术债务已到临界点**

jirascripts 与盗版 Jira 强耦合，任何扩展都需要在黑盒 API 上摸索。自建看板（jirascripts 前端工程）走到一半就遇到了这个天花板——数据源不可靠，边际价值递减。继续投入这条路，是在一个会死的地基上盖楼。

**系统已经在影响日常效率**

服务器卡顿、页面死掉不是偶发问题，是盗版系统无人维护、无法升级的必然结果。随着时间推移只会更差，不会自行好转。

### 4.2 现在切换的时机成本最低

| 优势维度   | 现状与机遇                                                                                          |
| ---------- | --------------------------------------------------------------------------------------------------- |
| 自动化平替 | **Plane 提供完整 GitLab 自动化能力**，轻量级微服务 `gitlab-bridge` 可完整替代沉重的 `jirascripts`。 |
| AI 工作流  | **Plane + opencode + MCP 开发工作流**已可接入，AI 辅助开发直接可用。                                |
| 架构可控   | **底层架构现代化且可控**，团队有能力对 Plane 进行源码级二开，不再受制于黑盒厂商。                   |
| 学习成本   | **团队已有 Plane 使用基础**，迁移学习成本低。                                                       |
| 数据迁移   | **历史数据可以归档不迁移**，不需要大规模数据搬迁，无沉重历史包袱。                                  |

### 4.3 结论

| 维度 | 结论                                                                        |
| ---- | --------------------------------------------------------------------------- |
| 合规 | 必须替换，无选项                                                            |
| 能力 | Plane 在可视化、AI、API、稳定性上全面超出盗版 Jira                          |
| 架构 | 现代化的 React+Django 架构，具备极高的二开友好度和长期演进能力              |
| 不足 | 自定义字段、Epic 等缺口有明确解法，且都在可控工作量内，且排除了人数限制误区 |
| 时机 | 现在是切换成本最低的时间窗口                                                |
| 建议 | 新迭代直接在 Plane 发起，正式宣告 Jira 退役                                 |
