---

在从 Jira 迁移到 Plane 的过程中，团队最常问的问题就是：“Jira 里的 Epic 和 Sprint 去哪了？”

本指南旨在解答这个疑惑。结论很简单：**Plane 完美保留了 Jira 的敏捷管理内核，只是换了更贴切的名字，并在界面逻辑上做了更清晰的解耦。**

| Jira 概念          | Plane 概念             | 核心作用                           |
| :----------------- | :--------------------- | :--------------------------------- |
| **Epic（史诗）**   | **Module（模块）**     | 按**业务功能**打包任务（空间维度） |
| **Sprint（冲刺）** | **Cycle（周期/迭代）** | 按**时间段**打包任务（时间维度）   |

---

## 疑问 1：Module 是什么？它是 Epic 的平替吗？

**是的，在实际使用场景中，你可以完全把 Plane 的 Module 当作 Jira 的 Epic 来用。**

它们都是为了解决“一个大需求无法在一个迭代内做完”的问题，将相关的 Issue（任务）圈在一起，方便进行宏观的进度追踪。

### 为什么在 Plane 中它变得更好了？

在 Jira 中，Epic 被设计成了一种特殊的“任务类型（Issue Type）”，你需要像建 Bug 一样去建一个 Epic。这种设计常常让人产生逻辑上的混淆（比如在任务列表里找 Epic）。

在 Plane 中，Module 被提升为与 Issue 平级的一等公民（左侧独立菜单）。

- **独立面板**：你可以为 Module 设定负责人（Lead）、目标完成时间。
- **专属数据**：点击任何一个 Module，都会展现该业务线专属的进度条和燃尽图分析报表。

**💡 迁移习惯提示：**

> 以前在 Jira：点击 `新建任务 -> 类型选择 Epic`。
> 现在在 Plane：点击左侧菜单 `Modules -> Create Module`，然后将具体的 Issue 关联进去。

## 疑问 2：Cycle 和 Module 是什么关系？谁包含谁？

在接触新的系统时，很多人会问：“Cycle 包含了 Module，还是 Module 包含了 Cycle？”

**答案是：它们是平级的、正交（交叉）的关系，不存在谁包含谁。**
这也正是 Jira 中 Sprint 和 Epic 的真实底层关系（尽管 Jira 的某些折叠视图会让人误以为它们是父子关系）。

无论是 Jira 还是 Plane，最底层的原子都是 **Issue（任务）**。

- **Module（Epic）** 和 **Cycle（Sprint）** 只是给这个任务贴上的**两个不同维度的标签**。

**一个真实的业务场景：**

- 一个 **Module（例如：开发购物车功能）** 通常很大，它需要跨越 Cycle 1、Cycle 2 才能全部做完。
- 一个 **Cycle（例如：本周双周迭代）** 里，开发人员可能同时在做属于“购物车 Module”的任务和“用户中心 Module”的任务。

Plane 的 UI 把时间线（Cycle）和业务线（Module）彻底解耦，这比 Jira 更加符合敏捷的本质。

## 疑问 3：当 Module 或 Cycle 做完后，该怎么处理？

### 状态流转与竣工

像 Jira 一样，Plane 的 Module 和 Cycle 都有自己的生命周期状态。

- 当关联的最后一个任务变成 Done 时，Module/Cycle 的进度条会达到 100%。
- 此时，项目负责人需要手动将其状态改为 **Completed（已完成）**，相当于“竣工剪彩”。

### 强大的 Archives（归档）机制

为了保持日常看板和工作区的清爽，Plane 原生提供了一个物理隔离的 **Archives（归档库）**，完美替代了 Jira 中繁琐的“隐藏已完成 Epic”的过滤操作。

- 你可以将已经完结很久的 Module 或 Cycle **一键 Archive**。
- 它们会从活跃视图中彻底隐藏，但所有的数据沉淀（任务历史、燃尽图）都会被完美保留在项目专属的 Archives 菜单中，供随时复盘或恢复。

---

## 总结

Plane 没有发明新概念，它只是把 Jira 中由于历史包袱导致有些混乱的模型，重新梳理成了一个极其干净的坐标系：

- 横坐标：**Cycle (Sprint)** 负责控制时间节奏。
- 纵坐标：**Module (Epic)** 负责拆解业务功能。
- 坐标里的点：**Issue (Task/Bug)** 负责具体干活。

团队只需要花费 5 分钟适应名词的改变，就能在这个更加现代化的平台上，延续我们熟悉的敏捷研发节奏。
